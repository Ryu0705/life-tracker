## 0. 前提として確かめた事実
- タブは今 2 つ（`LifeTrackerApp.swift`: 予定・トレーニング）。睡眠タブで 3 つになる
- アプリの暦は JST 固定（`calendar.timeZone = Asia/Tokyo`。DB 側も `jst_today()` と `AT TIME ZONE 'Asia/Tokyo'`）
- 睡眠の行かどうかの判定は `category.sub_input_kind = 'sleep'` だけ。アプリの「種類を新しく作る」は名前だけで kind を付けないので、kind = sleep の種類は seed の「睡眠」1 つ
- 0007 で睡眠に固有なのは: `checkin_set` の `p_sleep_score` 引数と「スコアは睡眠だけ」の検査・`sleep_actual_input` の upsert/delete、`sleep_score_range` 制約。Swift 側は `CheckInOperation.set(sleepScore:)`・`ActualTask.sleepScore`（埋め込み decode）・`select=*,sleep_actual_input(sleep_score)`・`CheckInPlanner` の睡眠分岐 4 か所（`showsCircle`・`acceptsActual`・`actualLine`・`circleStyle`）・`CheckInSlot.isSleep`・`SleepActualSection`・モックの初期データ（一昨日の睡眠 23:40–7:10・スコア 4）
- commit 済みの HEAD のアプリは `sleep_actual_input` を読んでいない（`git show HEAD:…SupabaseDayDataSource.swift` に無い）。つまり 0007 を直しても、旧ビルドが壊れる経路は無い
- 前例: トレーニングを独立させたとき、`gym_actual_input` は migration 0003 で DROP し、`workout_session` は `actual_task` に従属させなかった（domain-model v16）
- 規約 C-8 は既に「sleep は actual 生成なし」と書いている。分ける方向は C-8 の元の考えに戻ることになる
- `ScheduleStage2Tests` のうち睡眠の回を「ただの繰り返しの予定」の例として使っているテストがある（`deletingOccurrenceRemovesSkippedKeepsDone`・`deletingWholeSeriesRemovesSkippedAndUnlinksDone`・`endingSeriesFromTodayKeepsPastDoneAndRemovesSkipped`・`circleShownByOccurrenceDayNotViewDay` の並び順確認など）。睡眠専用のテストは `SleepCheckInTests`（`afterMidnightBedtimeAttachesToPreviousOccurrence`・`tonightAcceptsActualOnlyAfterBedtime`・`clearingSleepRecord`）

## 2. 破壊パターン（壊れ方と推奨の対処）

### 2-1. 0 時過ぎの就寝がどの夜に付くか
- 壊れ方: 「就寝の暦日」で夜を決めると、0:30 に寝た記録が次の夜に付く。段階 2 のレビュー §3-1 で時刻の重なりの取得が 0 時過ぎの睡眠を落とした前例がある
- 推奨: 夜の決め方を **1 つの pure 関数**にする。案は 2 つで、どちらも「時刻を 1 つ決めて JST の暦日にする」形
  - (a) 起きた日（起床の JST 暦日。Apple ヘルスケアと同じ。domain-model の Phase 2 予定「endDate＋18:00 境界」もこれ）
  - (b) 寝た夜（就寝 − 12 時間の JST 暦日。0:30 就寝 → 前日の夜）
- どちらにするかは本人に聞く（§5 Q1）。守護派の条件は「**保存する列にしない、または保存しても規則を変えたら作り直せる**」こと。就寝・起床の生の時刻だけが正で、夜は導出（規約 C-6「派生元データと同期カラムの二重管理禁止」）

### 2-2. 予定タブの行と記録の結びつけ（表示時判定）
- 壊れ方 1: 「夜の日付 = 回の日」で結ぶと、予定の開始が 0 時以降の世代（例: これ以降を 1:00〜9:00 に変えた）で崩れる。1:00 の回の「回の日」は D だが、その夜に 0:50 に寝た記録の夜は D−1（規則 (b)）または D（規則 (a)）で、規則によって合ったり合わなかったりする
- 壊れ方 2: 世代が変わる境目の朝（D−1 は 23:00〜7:00、D は 1:00〜9:00）には、D の一覧に睡眠の行が 2 つ（前日から継続＋D の 1:00 の回）並び、1 件の記録が両方に重なる
- 推奨: **時刻の重なりで結ぶ**。記録 r と回 o（clip 前の本来の範囲）の重なりが正なら候補、各記録は重なりが最大の回 1 つにだけ付ける（同じなら早い回）。1 つの回に複数付いたら最も長い記録を出す。これで V-2〜V-4 が日付規則に依らず成り立つ。段階 2 のジム（C4）は「回の日にセットがあれば」だったが、睡眠は日をまたぐので日付での判定をまねない
- この判定は表示専用の pure 関数（DB に結果を書かない。D-4 OK 例 1）

### 2-3. 予定時刻が変わった世代の夜
- 壊れ方: 「予定の時刻 ±12h で就寝の入力時刻を解釈する」今の `CheckInPlanner.nearest` を睡眠タブに持ち込むと、睡眠タブは予定に依存してしまう（予定を消した夜・除外日の夜は基準が無い）
- 推奨: 睡眠タブの時刻の解釈は**予定を見ない**。「どの夜の記録か」を先に選び（既定 = 昨夜）、その夜の基準時刻（例: 夜の日の 21:00）±12h で就寝を、就寝の後で最初のその時刻で起床を決める。既定の時刻に予定の時刻を使うのはよい（入力の手間のため）が、予定が無くても既定（前回の記録 or 23:00/7:00）で動くこと

### 2-4. 予定が無い夜・除外日の夜・祝日
- 事実: 除外日の夜は予定の行が出ず、翌朝の前日継続も出ない（段階 1）。祝日は「祝日も出す」の予定だけ出る（睡眠は出す設定）
- 壊れ方: 予定タブ経由でしか見えない作りだと、その夜の記録が見えなくなる（C-2 の情報減少）。逆に予定タブで行の無い記録を「予定外」として出すと、段階 2 の予定外の一覧規則（`listItems`）に睡眠が混ざる
- 推奨: 睡眠タブは予定の有無に依らずすべての記録を出す（V-5）。予定タブは**結べた行にだけ**出し、結べない記録は予定タブに出さない（予定外の行も作らない）。予定タブの `listItems` は `actual_task` だけを見るまま

### 2-5. 重複記録（同じ夜に 2 件）
- 壊れ方: 入口が睡眠タブ 1 つでも、「昨夜」を 2 回保存・保存中の 2 度押し・過去日の記録を別の日に入れ直す、で同じ時間帯に 2 件できる。段階 2 で `ScheduleStore.perform` の 2 度目のタップが黙って捨てられた前例あり
- 推奨: 「1 夜 1 件」の一意制約ではなく「**記録同士は時間が重ならない**」を規則にする（昼寝を後で足しても規則を変えずに済み、夜の規則（§2-1）を変えても制約を作り直さなくて済む）。RPC で重なりを検査して拒否（文言「この時間には記録があります」＋その記録を開く）。最後の砦として排他制約（`EXCLUDE USING gist (tstzrange(bed_at, wake_at) WITH &&)`、btree_gist 不要の範囲型だけで書ける見込み。**使い捨て Postgres と Supabase で使えるかは未確認**）。保存中はボタンを押せなくする

### 2-6. 時刻の逆転・24 時間超・0 分
- 壊れ方: 起床を就寝より前にする・同じ時刻・日付ピッカーで翌日を選び忘れて 24h 超
- 推奨: 入力は時刻（時:分）だけにし、起床は「就寝の後で最初のその時刻」（今の `CheckInPlanner.end` と同じ。同じ時刻は保存不可）にすれば逆転は UI で起きない。DB は `CHECK (wake_at > bed_at AND wake_at - bed_at <= interval '24 hours')`。24 時間でなく 16 時間などにするかは本人の実態次第（徹夜明けの長い睡眠）なので上限は緩めに

### 2-7. 昼寝と本睡眠の誤判定
- 壊れ方: 時刻（例: 9〜18 時に始まるのは昼寝）や長さで自動判定すると、夜勤明け・徹夜明けの朝寝を昼寝と誤る。推移グラフの「睡眠時間」に昼寝が混ざる／抜ける
- 推奨: **自動判定しない**。昼寝を記録するかどうか自体を本人に聞く（§5 Q2）。記録するなら種類の列（本睡眠／昼寝）を本人が選び、既定は本睡眠。予定タブの睡眠の行に付けるのは本睡眠だけ。段階 2 で決めた「昼寝などの 2 回目は予定外の実績で記録」（AI 既定）は、睡眠を actual_task から外す決定と矛盾するので取り消す（S2-6）

### 2-8. タイムゾーン
- 推奨: 生の時刻は timestamptz、夜・暦日の導出は Asia/Tokyo 固定（アプリの calendar と DB の `jst_today()` に合わせる）。端末のタイムゾーンを使う `Calendar.current` を睡眠タブで使わない（既存の JST 固定の calendar を注入）

### 2-9. 読み込み範囲（予定タブ）
- 壊れ方: 今の実績の取得は `occurrence_date IN (D-1, D)`。睡眠の記録には occurrence_date が無いので、同じ取り方はできない。D の一覧に出る睡眠の回は「D−1 の回（前日継続）」と「D の回（翌朝まで続く）」で、D の回が 0 時以降開始の世代なら D の朝の分も含む
- 推奨: 時刻の重なりで取る: `wake_at > (D−1 の 0:00 JST) AND bed_at < (D+2 の 0:00 JST)`。広めに取り、どの行に付くかは §2-2 の pure 関数が決める（表示範囲 ⊆ 読み込み範囲。規約 D-1）

### 2-10. 過去日の編集
- 事実: 予定は過去日を変えられない（D ≥ 今日）。実績は過去日も入力可
- 推奨: 睡眠の記録は実績の側なので過去日も入力・修正・削除可、未来だけ拒否（R-3・R-5）。予定の「過去は変わらない」と混同して睡眠の過去日を読むだけにしない

### 2-11. 予定の削除・変換で睡眠の記録が影響を受けない
- 推奨: 記録の表は予定へ FK を持たない（C-1）。段階 2 で予定側の RPC に足した「skipped を消す・done のつながりを外す・つなぎ直す」は `actual_task` だけの話で、睡眠の表には何も足さない。D-4 の 9/30 改訂（緩い参照）は睡眠には使わない＝改訂の範囲を広げない
- これで「予定を消したら睡眠の記録が予定外として残る」等の段階 2 の睡眠向けの扱い（`deletingOccurrenceRemovesSkippedKeepsDone` の睡眠の例）は、睡眠については不要になる

### 2-12. 旧 `sleep_actual_input` と actual_task の睡眠の行の後始末
- 事実: 本番は 9/30 時点で actual_task・sleep_actual_input とも 0 件（walkthrough「現状」）。0007 は未適用なので、アプリから睡眠の actual_task を書いた経路はまだ無い
- 推奨:
  1. 適用前に本番の件数を読むだけで確かめる（`SELECT count(*) FROM actual_task a JOIN category c ON … WHERE c.sub_input_kind='sleep'`、`SELECT count(*) FROM sleep_actual_input`）。0 件なら移行の SQL は書かない。0 件でなければ移行（時刻 → 睡眠の表、スコアも）を書いてから消す
  2. `sleep_actual_input` の DROP は、段階 1 で決めた「追加と削除の migration を分ける」（DB §1-6）に合わせ、**旧列の削除の migration（今の呼び名 0008）に同梱**する。トレーニングのときの `gym_actual_input` の DROP（0003）と同じ扱い
  3. `category.sub_input_kind` の 'sleep' は残す（予定タブで睡眠の行を見分けるのに使う）

### 2-13. 0007 から何を残し何を抜くか

## 3. データの持ち方への守護派の条件（推進派・データ担当の案を判定する基準）
1. 正は就寝・起床の生の時刻（timestamptz）だけ。夜・暦日・睡眠時間・昼寝かどうかは導出か本人の明示
2. 予定の表への FK・参照を持たない（template_id・occurrence_date を持たない）。結びつけは表示時（§2-2）
3. category を参照しない（睡眠の表＝睡眠。R-7）
4. 制約: 就寝 < 起床・上限 24h・スコア NULL か 1〜5・時間の重なり禁止（RPC＋可能なら排他制約）
5. 書き込みは RPC（未来の拒否・重なりの検査を 1 か所に。段階 1・2 と同じ流儀）。RPC は睡眠の表以外に触れない
6. 「開始だけ（寝ている最中）」の行を作らない（就寝・起床とも必須）。入力の前後に儀式を挟まない（memory feedback_input_ux）
7. HealthKit は範囲外（C5 の C 案のまま）。今の列に `source`・`healthkit_sample_uuid` を先回りで足さない（足すときは NULL 可の列追加 1 行で済む）

## 5. 推進派が攻めすぎたときに止める基準
| 基準 | 線 |
|---|---|
| タブの数 | 3 つまで（予定・トレーニング・睡眠）。睡眠の「分析」を別タブにしない。推移は睡眠タブの中 |
| 毎朝の入力の手数 | 睡眠タブを開く → 昨夜の就寝・起床が既定で入っている → 直す（任意）→ 保存、の **2 タップ＋直す分**まで。スコアは任意のまま（必須にしない） |
| 儀式 | 「寝る」「起きた」ボタン、就寝前の通知からの必須入力、オンボーディングは作らない（memory feedback_input_ux。C5 B 案「毎朝の専用シート＝儀式」を不採用にした理由と同じ） |
| 入口の数 | 入力の入口は睡眠タブだけ（10/1 本人決定・C-7）。予定タブの行に「記録する」ボタンを足さない。ウィジェットからの入力も今回は作らない |
| 項目 | 就寝・起床・スコア（任意）まで。睡眠の質の内訳・目覚めの回数・メモ・寝つきまでの時間は本人が求めるまで足さない |
| 推移 | グラフは 1〜2 種類（睡眠時間／就寝・起床の時刻の帯）。予定との差の分析・継続の仕組み（連続日数・リング）・ウィジェットは今回入れない（継続の仕組みはトレーニングの本人決定で、睡眠への拡張は未決） |
| 予定との結合 | DB で結ばない（§3-2）。「予定どおり寝られた率」等の集計を DB に置かない（D-4 NG 例 3） |
| ヘルスケア | 今回は作らない（範囲外の決定のまま） |
| 作る量の目安 | 新しい表 1・RPC 2〜3（保存・削除）・タブ 1（一覧＋推移＋入力シート）・予定タブの表示関数 1。これを超える案は「本人の決定に必要か」を個別に問う |

## 7. 要約
- 分けることで段階 2 の睡眠向けの例外（丸なし以外）はほぼ全部消せる。残すのは丸の幅取り・スキップを出さない・予定タブの「実績 …」表示だけ

- 睡眠を例に使っていたテストは種類を替えて検査を残す

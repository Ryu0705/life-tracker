### 1-2. S1「起床日 = D+1」で結ぶ: No の理由
- 予定の開始は `start_minutes_from_midnight` 0〜1439（CHECK）【事実】。推進派の挙げた「25:00 開始」は持てず、1:00〜9:00 の予定になる。この回の回の日は D で、起きる日も D。「起床日 = D+1」の規則だと、その夜の記録（D 1:10 → D 9:00、起床日 D）は **D−1 の回の行に付く**＝1 日ずれた夜に出る（V-4 No）
- 世代の境目（D−1 は 23:00〜7:00、D から 1:00〜9:00）では、D の一覧に睡眠の行が 2 つ並び、起床日の規則ではどちらに付くかが日付だけで決まり、時刻の実態と合わない（V-3・V-4 No）
- 早寝して 0 時前に一度起きた夜（22:00–23:50 と 0:30–7:00）が 2 つの起床日に割れる（データ担当 §2-1 の表で N2 ✕【事実】）
- 夕方の寝落ち（18:00–23:00）は起床日の「夜の睡眠」になり、その夜の本番が 2 件目になる。推進派は自動分類で逃がすとしているが、分類の境界（起床 12:00〜20:00）とデータ担当の境界（就寝 18:00〜翌 6:00）が食い違っている
- 対処: 予定の行へは**時刻の重なり**で付ける（重なりが最長の行 1 つ）。これは日付の規則に依らないので、上の 3 つとも崩れない

### 1-3. S2「1 朝 1 件」の一意制約: No の理由
- 夜／昼寝の種類を自動で選んで `kind` に保存するため、誤分類された記録は一意制約をすり抜ける。例: 夜の睡眠 23:00–7:00 と、昼寝と判定された 6:00–8:00 が**重なったまま両方入る**（R-4 No）
- `wake_date` を保存すると、時刻を直したのに日付を直し忘れる経路ができる（C-6・INV-5 No）。RPC で入れると書いているが、推進派の §4 は書き込みの経路を決めていない
- 分割した夜（中途覚醒で 2 件に分けたい）が入れられない
- 対処: データ担当の EXCLUDE（時間が重なる 2 件を禁止）。上書きの確認（「この朝の記録を上書きしますか」）は、重なりで止まった（23P01）ときに「この時間には記録があります → 開く」として出せば、推進派の UX はそのまま守れる

### 1-4. S3 今朝のカードの既定値
- 就寝の既定 = 「その夜の予定の就寝」。予定が無い夜（除外日・予定を消した後）には既定が無い（守護派 §2-3）。→ 既定の順を決める: その夜の予定 → 直近の記録の就寝 → 23:00
- 「その夜の予定」は前日の世代で組み立てた回（段階 1 の「前日の分は前日の世代」）を使うこと。今日の世代を使うと、世代が変わった朝に違う時刻が入る
- 起床 = 開いた時刻（5 分切り捨て）。予定の起床 −2h〜+5h の外では予定の起床。昼に開くと 11:00 起床で記録される恐れは推進派の窓で抑えられている。未来は入らない（切り捨てなので R-3 は Yes）
- 1 タップで予定どおりの時刻が記録されるので、ずれを直さずに押すと「予定どおり寝た」記録が増え、推移が予定に寄る【推測】。ただし段階 2 の C3（丸 1 タップ = 予定の時刻どおり）で本人が同じ性質を受け入れている【事実: walkthrough C3】ので、守護派はこれを止める理由にしない。カードに睡眠時間と予定との差をその場で出す（推進派の案どおり）ことを条件にする

### 1-5. S8「睡眠タブで直す ›」
- 入力部品を置かず、睡眠タブへ移るだけなら V-1（予定タブで入力しない）と C-7（同じ機能のボタンを並べない）は Yes
- 壊れ方: タブの切り替え＋そのタブでシートを開く、を 1 回の操作でやると、予定の編集シートが開いたまま別タブのシートを出そうとして出ない／二重に出る（SwiftUI でシートの上にシートを出す既知の扱いにくさ【推測】）。予定の編集シートを閉じてから切り替える順序が要る
- 対処: 置くなら「予定の編集シートを閉じる → 睡眠タブへ → その夜のシート」の順をテストで固定する。置くかどうかは守護派 Q3（過去日の睡眠の行を押したときの動き）と合わせて本人に聞く

### 1-6. S10 🔥 連続
- 継続の仕組みは 9/30 の本人決定で**トレーニングの**「週 N 回」を基準にしたもの【事実: continuity-design】。睡眠に連続を出すのは新しい方針で、AI の既定で入れる範囲を超える（AGENTS「選好の問題や新しい方針は決定を本人に渡す」）
- 壊れ方: 同じ「🔥 n日」の見た目で意味の違う 2 つの連続（トレーニング = 目標週の連続、睡眠 = 記録した朝の連続）が並ぶ。`StreakViews` を使い回すと、トレーニングの部品を睡眠向けに変えたときにウィジェット（同じ部品を共有）に響く（C-6・C-7 が No になりうる）
- 対処: 今回は作らない。本人が望めば「何を数えるか」を決めてから、トレーニングの `Continuity` とは別の pure 関数で作る（共有部品を変えない）

### 1-7. S6 左スワイプで確認なしの削除
- 睡眠の削除・修正は本人が「少し考えたい」と保留にしている論点【事実: walkthrough 保留 9/30】。推進派の案は予定外の実績と揃える筋の通った既定だが、保留中の論点を AI の既定で埋めない
- 守護派の推奨は、全スワイプ（`allowsFullSwipe`）を切り、スワイプ → 「削除」で消える形まで（段階 2 と同じ）。確認・元に戻すを足すかは本人に聞く

### 1-8. S9 推移 6 種
- 「予定との差の累計（直近 14 日）」は、睡眠タブが過去 14 夜分の予定（世代・除外日・祝日）を組み立てる必要がある。予定タブの DayBuilder を日数分回すことになり、睡眠タブが予定のデータ経路に依存する（D-4 の UI 層の結合としては OK だが、作る量と壊れる場所が増える）
- 対処: 今回は範囲バー（予定の帯なし、または固定の 23:00–7:00 でなく今の世代の帯 1 本）・睡眠時間・スコアの 3 種。予定との差と就寝のばらつきは、使われ方を見てから

## 2. データ担当の案は守護派の懸念を解消するか

| データ担当の案 | 守護派の懸念 | 判定 | 残る点 |
|---|---|---|---|
| 夜の日 = 就寝 − 12h の JST 日、表示時に計算（保存しない） | 2-1 夜の決め方・C-6 導出値の保存・R-8 | **解消** | 計算する関数は 1 つ（`SleepNight.key`）に限り、睡眠タブ・推移・予定タブが同じ関数を呼ぶこと（新しい項目 N-1） |
| 予定タブとは時刻の重なりで結ぶ。1 件が 2 行に重なれば重なりが長い方（同じなら早い行） | 2-2「日付で結ぶ危険」・V-3「2 行に二重に出る」・V-4 | **解消** | 1 つの行に複数件（分割した夜）は「まとめて 1 行に出す」。V-3 の「1 行に記録は 1 件」をこれに合わせて直す（§4） |
| 昼寝 = 就寝が 18:00〜翌 6:00 以外（表示時に分類・列なし） | 2-7「自動判定しない」 | **一部解消**（守護派が緩める。§3） | (a) 分類は保存しないので誤っても定数を変えれば直る＝守護派が恐れた「データが壊れる」は起きない。(b) ただし予定の行への付け方は分類に依らず重なりで決めること（徹夜明けの 6:10–12:00 が「昼寝」でも、睡眠の予定 23:00–7:00 と重なればその行に出る）。この関係をテストで固定する（新しい項目 N-3） |
| EXCLUDE で重なり禁止（btree_gist 不要） | 2-5・R-4・R-10 | **解消** | 素の Postgres 16 で作れた【事実（データ担当）】。Supabase での作成と、PostgREST が 23P01 を返す形（HTTP 状態）は本番適用後に確かめる。アプリは 23P01 を「この時間には記録があります」に訳す（新しい項目 E-2） |
| 取得 `start_at < D+2 0:00 AND end_at > D−1 0:00` | 2-9・V-6（規約 D-1） | **解消** | 予定の長さ ≤ 1440 分なので、D の一覧に出る回（前日継続〜今夜の回）はこの範囲に収まる【事実（CHECK）】 |
| 書き込みは直接 insert/update/delete（RPC なし） | 守護派 §3-5「RPC で未来の拒否・重なりの検査を 1 か所に」 | **受け入れる**（守護派が緩める） | 重なりは EXCLUDE が DB で止めるので RPC は不要。未来の拒否はアプリだけになる → InMemory とアプリの検査を同じ関数にし、テストで固定（R-3 を直す） |
| `0007` から睡眠を抜き、`checkin_set`・`actual_save` で睡眠の種類を拒否 | 2-13・S2-6 | **解消** | 一致。「拒否を入れない案も可」とあるが、守護派は入れる側（S2-6 は DB で No にできる方がよい） |
| `0008_sleep_record`（`sleep_actual_input` の DROP を同梱・1 件でもあれば止まる砦）、旧列削除は 0009 | 2-12（DROP は旧列削除と同じ migration に） | **受け入れる**（守護派が緩める） | 守護派が DROP を後ろに回したのは「動いているビルドを壊さない」ためだったが、commit 済みのビルドは `sleep_actual_input` を参照しない【事実（双方で確認）】、本番 0 件、行があれば止まる砦付き。分ける理由が無い |
| 予定タブの読み直しは今日だけ（他の日のキャッシュは古いまま） | V-7 | **未解消** | 昨日を見ていたまま睡眠タブで昨夜を直すと、予定タブの昨日に古い「実績」が残る。睡眠タブで書いたら予定タブの今日以外のキャッシュを捨てる（`ScheduleStore` の辞書を空にするだけ。読み直しは見たときに起きる）。費用が小さいので V-7 は残す |
| `-mock-day` で睡眠タブと予定タブが同じ state を共有 | （守護派は挙げていなかった） | 追加で採る | ジムの `-mock-workout` が別データになっている既知の問題を繰り返さない。新しい項目 M-1 |

結論: 守護派の 2 大懸念（日付で結ぶ危険・同じ記録が 2 行に出る）は、データ担当の「重なりで結ぶ・最長の行 1 つ」で解消する。残るのは V-7（キャッシュ）だけ。

## 3. 譲歩と自己採点

### 3-1. 推進派の UX で守るべきと認める点（譲歩）
| 推進派 | 認める理由 |
|---|---|
| 今朝のカード（予定で埋めて 1 タップ） | 段階 2 C3 で本人が「予定どおりで 1 タップ」を選んでいる。0007 の予定タブ経由（4 タップ・予定の編集画面を経由）より短く、儀式でもない。守護派の止める基準（2 タップ＋直す分）の中 |
| 見出しを「10/2(金) の朝」と呼ぶ | 夜の**キー**（就寝 − 12h）とは別に、見出しの**文言**は「キー + 1 日の朝」と出せる。分割した夜も同じ朝になる。どちらで呼ぶかは文言だけの違いなので、推進派の「朝に入れるのに昨夜を選ばせない」を採ってよい（本人に聞く Q1 はそのまま残すが、推奨を推進派側に移す） |
| [−15][+15]・ホイール、日付を出さない | 時刻だけの入力は守護派の 2-6（逆転を UI で起こさない）と同じ |
| 予定タブの「未入力」表示 | 守護派は「出さない」を推奨したが、データ担当も今の「今夜の回は就寝の予定時刻まで出さない」規則を残す案。規則が pure 関数でテスト済み（`tonightAcceptsActualOnlyAfterBedtime`）なら、入力の促しとして残す価値のほうが大きい。守護派は撤回 |
| 直近 7 朝の未入力の行 | 記録し忘れの入口として必要。過去日の入力（R-5）を自然に満たす |
| 「睡眠タブで直す ›」 | 移るだけなら V-1・C-7 を壊さない（§1-5 の順序の条件つき） |

### 3-2. 守護派の Round 1 で緩めてよい点（自己採点）
| Round 1 の主張 | 採点 | 理由 |
|---|---|---|
| 書き込みは RPC（§3-5） | **緩める** | 1 行で完結・過去日も可・重なりは EXCLUDE が止める。トレーニングの直接書き込みと同じ流儀で足りる |
| `sleep_actual_input` の DROP は旧列削除の migration に（§2-12） | **緩める** | §2 の表のとおり、分ける理由が無い |
| 昼寝を自動判定しない（§2-7） | **緩める** | 分類を保存しないなら誤分類は表示だけの問題で、定数を変えれば過去分も直る。種類を毎回選ばせる手間（推進派の記録シートの切り替え）より軽い。ただし昼寝を記録するか自体は本人に聞く（Q2 は残す） |
| V-3「1 行に付く記録は 1 件」 | **直す** | 分割した夜を 1 行にまとめて出す方が実態に合う |
| 推移は 1〜2 種 | **少し緩める** | 3 種（範囲バー・睡眠時間・スコア）まで |
| 「未入力」を出さない（§4） | **撤回** | §3-1 |
| 夜の呼び方は寝た夜を推奨（Q1） | **推奨を変える** | 見出しは朝でよい。キーは就寝 − 12h のまま |
| 予定へ FK を持たない・重なりで結ぶ・保存した日付列を持たない・重なり禁止・0007 から睡眠を抜く | **維持** | データ担当と一致。推進派の `wake_date`・`kind`・一意制約はこれに反する |
| 🔥・確認なし削除を AI の既定で入れない | **維持** | 新しい方針・保留中の本人論点 |
| V-7 キャッシュ | **維持** | 費用が小さい |
| 24 時間の上限 | **維持** | データ担当と一致（`<= 24h`。推進派は `< 24h`。どちらでもよいが 1 つに） |

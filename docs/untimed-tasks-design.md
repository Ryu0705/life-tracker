## データの持ち方（AI 案・レビュー前 2026-10-13）
前提（事実）: 本番 DB は 0011 まで適用済み（2026-10-13 `list_migrations` で確認。hyngpesrmqodiegonoze）。時刻つきの予定は「系列 task_template ＋世代 task_template_version ＋除外日 ＋その日だけ変えた回 scheduled_task(template_id) ＋単発 scheduled_task」、実績は actual_task（回ごとに 1 行、done は時刻必須・skipped は時刻なし）。DayBuilder・CurrentBlockCard・睡眠・ジムの判定は時刻の範囲（visibleRange）前提。

### 案 A′（AI の推し）: 系列・世代・回の仕組みは共有し、時刻の有無を中身の 1 項目にする
- DB: `task_template_version` と `scheduled_task` の時刻の列を NULL 可にし、`target_count INT`（時刻なしのときだけ・1 以上）と `carry_over BOOLEAN`（繰り返しのときだけ意味を持つ。単発は常に繰り越す）を足す。時刻なしの単発は `scheduled_task.date DATE` で日を持つ。CHECK で「時刻あり（開始・終了）」か「時刻なし（日・目標回数）」のどちらか一方に限る
- 実績: `actual_task` に `count INT` と `done_at TIMESTAMPTZ`（目標に届いた時刻）を足す。時刻なしの回は時刻 NULL のまま done／進行中（count < 目標）を持てるよう time_chk を分ける。回のキー（template_id＋occurrence_date／scheduled_task_id）と「1 回に 1 行」はそのまま
- Swift: `ScheduleContent` の時刻を `timing: .timed(start, duration) / .untimed(target)` にする。DayBuilder は入口で時刻なしを分け、`Day.todos: [DayTodo]` として別に出す（`DayScheduledTask` と `ScheduledTask.startAt` は時刻つきのまま = 時刻の判定を使う処理は触らない）
- 得るもの: 「この予定／これ以降」・その日だけの変更・削除・単発↔繰り返しの変換の RPC と規則がそのまま使える。時刻あり↔なしの切替（決定 8）は「これ以降の中身の変更」になり、過去の回の記録は残る
- 失うもの: 時刻の列が NULL になり得るので、時刻つきだけを想定した SQL・関数を全部見直す必要がある

### 案 B: 別の表（todo_template / todo_version / todo / todo_record）
- 時刻の処理には一切触れない。代わりに世代・除外日・その日だけの変更・削除・変換の仕組みを複製する。時刻あり↔なしの切替は表をまたぐ移動になり、実績のつなぎ直しが要る

### 両案に共通の論点（レビューで確かめる）
- 繰り越しの取得範囲: 終わっていない過去の回をどこまで遡るか（毎日・繰り越しオンを 1 年放置 = 365 行）。上限・遡る起点が要る
- 回数の記録を「数（count）」で持つか「タップ 1 回 = 1 行」で持つか（後者は何時ごろやったかが残るが行が増える）
- 「やった日に記録が付く」（決定 7）と、回のキー（元の日）の両立
- migration 番号: 0012 は「旧列の削除」に予約済み（0006 の注記）

## レビュー結果（2026-10-13・opus のサブエージェント。主要 3 点は AI が実コードで確認済み）
推奨は **案 A′**（時刻あり↔なしの切替が「これ以降の中身の変更」1 回で済み、系列 id・過去の世代・実績のつながりが残る。規則の原本＋SQL の写しが 2 組にならない。繰り越しはどちらの案でも新規）。ただし次を直す。
- `scheduled_task.occurrence_date DATE NOT NULL` を全行に足し（時刻ありは start_at の JST 日で backfill）、RPC の日の判定と一意索引（0001:94-96 は start_at の式）をこの列に置き換える
- Swift は取得の境界で時刻あり／なしを分ける。`ScheduledTask`・`TaskTemplate`・`DayScheduledTask` は時刻必須のまま、時刻なしは別の型（`Day.todos`）。DayBuilder・CurrentBlockCard・SleepRules・既存テストのコンストラクタ 34 か所は変えない
- 実績は `count INT`（絶対値で送る）と `closed_on DATE`（目標に届いた日／スキップした日）。完了は保存せず「count ≥ その回の世代の target」で表示時に判定。回のキー・1 回 1 行・checkin_set の upsert はそのまま
- 見せる条件: 回の日 ≤ 見ている日 V かつ（closed_on が NULL か closed_on ≥ V）。closed_on = V の日は「完了（元の日 から）」
### 重大
1. 旧ビルドは時刻なしの世代が 1 行できると予定タブ全体（睡眠タブの予定も）を読めなくなる（TaskTemplateVersion の時刻が非 optional・世代は全件取得 SupabaseDayDataSource.swift:33-36）。順序は migration → 新ビルド → 時刻なしを作る。作った後は旧ビルドに戻せない
2. 繰り越した単発は今の規則だと過去日扱いで削除・編集できない（schedule_single_delete 0007:192-197 の schedule_assert_editable）。時刻なしで閉じていない単発は日付に関係なく編集・削除できるようにする
3. 時刻 NULL で壊れる SQL が多数（save_following / delete_following / occurrence_save / occurrence_delete / single_save / single_delete / checkin_set の日の判定、task_template 旧列 NOT NULL、delete_following の列の写し、time_chk に時刻なし done の枝）
4. 実績の取得（occurrence_date IN (D-1, D)）とキャッシュ破棄（前後 1 日）を繰り越し用に広げる
### 中
- RPC の引数追加は PostgREST のオーバーロード（PGRST203）の恐れ【推測】→ 使い捨て Postgres で確認
- 時刻なしでは睡眠の種類を出さない（checkin_set が睡眠を拒否）。ジムのセット判定は時刻つきだけ
- 祝日は休日パターンの予定だけ出る・「何もしない日」は全部止まる、が時刻なしにも効く（意図と合うか要確認）
- つながりの切れた時刻なしの done は一覧に出ないまま残る（予定外は startAt != nil のみ表示 CheckIn.swift:219）
- migration: この機能が 0012 を使い、旧列の削除を 0013 に下げる（予約の書き直し先は day-cycle-walkthrough.md・domain-model.md・0006・0011 の注記）

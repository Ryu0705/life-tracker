## 2. 反論（B が守りすぎて Gymwork の効き目を削っている点）

### R1. 「完了操作を作らない」自体には同意。ただし B の代替案は Gymwork の効き目を半分しか拾っていない
- Gymwork の「完了」は儀式として嫌われているが、そこには 2 つの効き目がある: ①**今日の成果を 1 か所で見る報酬**（ヘッダーの kg / セット数が ✓ ごとに増える＋完了時の要約）②**今日のメニューが次回再利用できる形で残る**（ルーティン保存）
- B は D2 の回避策として「サマリーは今日のカード見出しに常時表示（既にボリューム表示あり）」としている。しかし現行は**種目単位**のボリュームしか無く、**その日全体の合計が無い**。種目が 4〜5 枚になると合計は暗算になる → ①の効き目が消えている。**P1（日の合計ヘッダー）は INV-1 を守ったまま①を回収する唯一の手**なので、「既にある」で済ませず必須扱いにしたい
- ②は B の案では「ルーティン保存は能動操作で」＝結局だれも保存しない（本人は「単純に何をしたのかを記録したい」人で、メニュー管理はしない）。**P4 は保存操作そのものを不要にして②を回収する**（過去の日がそのままルーティン）。INV-1 の精神（まとまりはアプリが記録から自動で作る）を最もよく満たすのは、名前付きルーティンより P4 のほう

### R2. INV-5 は方向は正しいが、文言が広すぎる
- 「導出値のためにテーブルを増やさない」は正しい（PR・週ボリュームを保存すると整合崩れの温床）
- ただし C が指摘した **PostgREST の 1000 行上限**への正攻法は DB 側の View / RPC による集計。これを INV-5 が「テーブルを増やす」と同列に禁じると、アプリ側で全件取得→ページングの複雑化を強いられる
- 提案: INV-5 を **「導出値を永続化しない（保存しない）。DB 側の View / RPC による読み取り時の集計は可」**に言い換える
- また INV-5 は「導出値」に限った話なので、**導出ではないデータ**（例: 今日の種目の並び＝plannedExerciseIds の永続化、日×種目メモ）の migration まで封じる根拠にはならない。今回は提案しないが、将来の判断を INV-5 で門前払いしないよう明記したい

### R3. ルーティンの置き場（B の C-2「種目追加シート内だけ」）は 1 タップ損する
- B のチェックリスト 1（起動→最初の ✓ のタップ数が現行以下か）で数えると:
  - 現行: タブ → ［種目を追加］→ 種目を選ぶ ×n → ［n種目を追加］→ ✓ ＝ 4＋n タップ
  - B 案（シート内に組み合わせ）: タブ → ［種目を追加］→ 組み合わせ → ［読み込む］→ ✓ ＝ 5 タップ
  - A 案（空の日だけ本画面にチップ）: タブ → チップ → ［読み込む］→ ✓ ＝ 4 タップ
- A 案はチェックリスト 1 で唯一「減る」。開始ボタン（D1）と違い、押さなくても何も欠けない（INV-1 の「押さないと欠ける設計は不可」に抵触しない）
- 妥協案: **本画面のチップは今日が空のときだけ出す**（種目が 1 つでも入ったら「前回の組み合わせ ›」の 1 行に畳む）。加えて B 案どおり**種目追加シートの上部にも同じチップ**を置く（途中で思い出した時用）

### R4. 週カレンダーはトレーニングタブに置くのが正しい（D7 への反論）
- B は今日タブの日付ナビ（Round 7 予定・未実装）との二重化を懸念。しかし意味が違う: 今日タブ＝「その日の予定と実績（時刻）」、トレーニングタブ＝「どの日にトレーニングしたか・その日の重量」
- トレーニングの過去日を今日タブの日付ナビに依存させると、過去の重量を見るたびに予実ビュー経由になる＝**トレーニング UI が今日タブに入り込む**（INV-7 の逆側の違反）。Round 5 まで今日タブとトレーニングは独立アグリゲート（INV-8）なので、ナビも独立が一貫している
- 同意する点: ①ヒートマップ・連続日数へ拡張しない（INV-6）②役割分担を spec / roadmap に 1 行書く（「トレーニングタブの週帯＝トレーニング履歴の閲覧専用。予実の日付切替は今日タブの担当」）③点は「記録がある日」の事実だけ

### R5. D12 で「筋肉の回復」を周辺機能（食事・AI と同列）に入れるのは分類ミス
- 食事 kcal・AI は別ドメインだが、部位ごとの最終トレ日は **workout_set からの導出＝トレーニング進捗そのもの**（INV-5 の範囲内、T8「部位 14 分割はハムだけ抜けているを検出するため」という本人向けの設計意図とも一致）
- ただし C の指摘（補助筋が無い＝ベンチの日も三頭が「回復済み」扱い）は正しいので、回復「度」や人体図は出さない。→ 単独 UI は撤回し、P4 のチップに経過日数を載せる／P5 の部位別表に「最終日」列を足す形で残す（§3）

### R6. 軽微
- B の C-7 は Round 4 の「連続週数」を許容しているが、Grit との二重管理（B 自身の D9）を避けるなら**連続週数も入れない**ほうが一貫する。推進派としても Gymwork の連続系は採らない
- B の C-1 は「分析タブ新設は可」。A は**タブを増やさない**（押し出し型の push）で良い。C-8「種目の推移に 2 タップ以内」も push 案で満たす（タブ → 種目名）

## 4. C の指摘を反映した修正版の提案リスト

### 共通の前提（C の 4 指摘への回答）
1. **1000 行上限**: 期間取得は必ず範囲を絞る（週単位＝多くても 1 週 150 セット程度）＋ `.range()` でページング。分析の複数週表示は「週ごとに取得」。既存の `fetchRecordedExerciseIds` の全件取得バグも基盤で直す（件数が少ない今のうちに）。集計 View / RPC は R2 の INV-5 言い換えが通れば選択肢に残す
2. **週の始まり**: **月曜始まりを推奨**（Gymwork も「9月28日(月)〜10月4日(日)」、月〜日表示）。`HomeView.defaultCalendar` 自体は変えず、トレーニング用に `firstWeekday = 2` を明示した calendar を作って渡す（今日タブへの副作用を出さない）。本人の小論点として確認
3. **読み取り専用の別 store**: `WorkoutHistoryStore`（週単位でロード・キャッシュ・書き込み API を持たない）を新設。**今日は既存の WorkoutSessionStore、過去日は HistoryStore** と分ける。週帯の「今日の点」は今日の store の sets から出す（記録直後に点が付く）。今日の store の load() に日付選択の状態を持ち込まない（下書き消失の回避）
4. **日の基準**: 集計・帯の点・過去日カードはすべて `completed_at` の JST 暦日。これを 1 つの pure function（dayKey）に集め、今日サマリー・過去日カード・週分析で共有（3 か所の数字を一致させる）。集計の定義も 1 か所: ボリューム＝weight_reps かつ本番セットのみ、セット数＝本番セット（W は別表記）

## 2. 反論（LT の良さを壊す／度が過ぎる点）

1. **縦方向の積み増しが「開いて ✓」を遠くする**（A のワイヤー: 週帯→合計→組み合わせチップ→回復→カード）。タップ数は同じでも、ジムでの最初の操作が「スクロールしてからカードを探す」に変わる。→ 今日の種目が1件以上あるとき、1画面目にカード先頭のセット行が見えることを受け入れ条件に加える（チェックリスト 1 の補強）
2. **P1 の経過時間**は「開始なし」の思想と相性が悪い。Gymwork の「運動時間」は開始ボタンの産物。LT で出すなら時刻の事実表示まで
3. **P2 を今日の store に同居させる実装**は、B の INV-3（最短経路）を実装経路から壊す（C 指摘 4）。設計で store 分離を必須にする
4. **P7 は Grit 境界の縁**。「経過日数」は事実だが、並べ方次第で「さぼりカウンター」になる。色・並び順（経過日数の長い順に並べない）まで指定したい
5. **A の Q2「3つ目のタブ分析」案**は不採用を推す。種目詳細の推移と二重の入口になり、今日タブの相対位置も下がる

## 5. 本人決裁に回す論点

### R-1 経過時間をヘッダーに出すか
- 要点: 現状（ヘッダー無し）→ 案a「1,440kg・9セット・3種目」のみ / 案b 上に加えて「8:12–8:40」（最初〜最新セットの時刻）/ 案c「28分」を動く時計で表示（Gymwork 同型）。守護派推奨 a or b、c は不採用推奨（開始なしの思想と衝突）
- エッジケース: セット1件目の時点で「8:12–8:12」「0分」になる／途中で休憩して昼に1セット足すと「8:12–12:30」になり実態より長い
- 可逆性: 表示のみ・DB 変更なし。いつでも切替可

### R-2 週の始まり（週帯・週分析）
- 要点: 現状 calendar は端末ロケール依存（ja_JP=日曜始まり）→ 採用後は月曜始まりを明示（Gymwork も月〜日）/ 日曜始まりを明示
- エッジケース: 日曜の深夜トレが週をまたぐ／今日タブの将来の週表示と揃える必要
- 可逆性: calendar 設定1か所。データ変更なし

### R-3 過去日の扱い: 読み取り専用で始めるか
- 要点: 現状 過去日を見る手段なし → 案a 読み取り専用（今回）＋編集は Round 4 / 案b 今回から追記・編集可
- エッジケース: 記録し忘れた昨日のセットを足したい（案a では足せない。MCP 直 INSERT で逃がす）
- 可逆性: a→b は差分追加で可（C: b の read-only 表示に編集を足す形）。b→a は編集で生じたデータの整合確認が要る

### R-4 「前回の組み合わせ」でルーティンを代替し、名前付きルーティンを Round 4 に残すか
- 要点: 現状 ルーティン UI なし → 案a 過去日の種目構成をチップで読み込む（保存操作なし）/ 案b 加えて今回から名前付き保存（routine CRUD、⋮ から能動保存・完了時ダイアログは出さない）
- エッジケース: 同じ日に胸と脚を両方やると「胸・脚」の組み合わせが1チップになり、次の胸の日に脚まで入る（読み込み確認シートで種目を外せること）
- 可逆性: a は表示と store 操作のみで可逆。b は routine テーブルにデータが入る（アーカイブで隠せる）

### R-5 分析の置き場
- 要点: トレーニングタブ右上から push（守護派・推進派とも推奨）/ 3つ目のタブ
- エッジケース: push だとジムで分析を見る頻度が低い場合でも問題なし。タブだと今日タブの相対的な地位が下がる
- 可逆性: 高（ナビゲーションのみ）

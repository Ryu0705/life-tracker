## 1. 対立ごとの判定と根拠

### 1-1 心肺の期間「強さと同じ期間」は本人決定か AI 既定か → **AI 既定（推奨を受け入れたときの付帯条件）。ただし結論（30 日のまま強さに残す）は変わらない**

最初に事実関係: brief では「推進派 = 本人決定、守護派 = AI 既定」と整理されているが、**Round 1 と Round 2 で両派の立場が入れ替わっている**【事実】。

- Round 2: 推進派「『同じ期間』まで含めて決まっている…読み落としていた」と譲歩（11 §2-2）／守護派「G-7 で『強さと同じ期間』を【本人】としたのは言い過ぎ…期間の部分は【AI既定】に下げる」と訂正（21 §2-2）

原文（`docs/body-strength-and-heatmap-period.md`）:

判定:
1. 本人が選んだ文言（`:66` の「」内）に期間は無い。期間が出てくるのは AI の推奨文（`:60`「期間内の」）と、回答後に AI が書いた言い換え（`:66` の「=」以下）だけ
2. 設計確定節（`:73`）自身が【本人】タグを「別ブロック・合計だけ」に限っていて、「強さと同じ期間」はタグの外に書かれている。docs の書き手（当時の AI）も期間を本人決定として扱っていなかった
3. ただし「推奨どおり」で受け入れた推奨文には「期間内の」が入っていたので、本人がまったく知らなかった条件でもない。区分は **【AI既定（推奨に含まれ、本人が推奨どおりと答えた付帯条件）】**。守護派 Round 2 の訂正が正しく、推進派 Round 2 の譲歩は理由（「本人が決めた」）が誤り
4. 同じ物差しを当てると、G-9 のうち「1か月｜半年の 2 段切替」は本人の文言（`:65`「**最小 1 か月・2 段切替**」）に入っているので【本人】、「色の閾値は半年分で固定」は `:65` の「=」以下にしかないので同じく AI 既定寄り。守護派 R1 は G-9 を一括で【本人】にしていたが、ここも分けて読むのが正確（今回の設計では閾値を変えないので影響なし）

### 1-2 種目ごとの推移の置き場 → **強さページの末尾**。見出し「種目ごとの推移」の右に「全期間」

候補と判定:
| 案 | 📊 → 種目 | 期間ナビとの誤読 | 判定 |
|---|---|---|---|
| (a) 強さページの末尾（推進派） | 2 タップ（既定 = 強さのとき） | ‹30日› はページ先頭で、一覧まで来るころには画面外。直上の心肺見出しに日付範囲、一覧の見出しに「全期間」を出して区別する | **採用** |
| (b) 中身ページの末尾（今の位置のまま） | 3 タップ | 中身ページは 1 画面に収まる長さになるので、‹今週› と一覧が**同じ画面に並び**、今より「この週の種目」に見える | 不採用 |

| (d) 4 つ目のセグメント「種目」 | 2 タップ | 起きない | 不採用（§4） |

根拠:
- 種目詳細で見るのは重さ・e1RM・回数・秒の伸び、つまり「強くなっているか」。強さページで部位の級を見たあと「その種目は伸びているか」へ進む流れになる（推進派 11 §2-1）
- 守護派の反論「トレッドミル・プランク・ハンドグリップも並ぶので強さだけではない」（21 §2-1-2）: プランク・ハンドグリップは級の対象（強さ）。トレッドミルは心肺で、心肺も同じ強さページにある。強さページ =「体の能力（筋力・心肺）の伸び」と読めば、一覧の全行がこのページの範囲に入る
- 守護派の反論「30 日で絞られて見える」（21 §2-1-1）: (b) よりは起きにくい（ナビが同じ画面にない）。見出しの「全期間」と心肺見出しの日付範囲で、期間つきの節と期間なしの節を見出しで区別する。これで十分かはスクショで確かめる（§6 S-6）
- 「強さページが長くなる」（21 §2-1-3）: 今の 1 枚より短い（強さ＋心肺＋一覧で、継続と週の部分が抜ける）。一覧は末尾なので、強さを見るだけなら一覧はスクロールしなければ目に入らない
- 今日のカード見出し → 推移（1 タップ）は変えない（`gymwork-alignment-design.md:56`）
- 2 タップ（C-8）は AI の判定で本人の発言ではない（21 §3 の訂正を確認: `gymwork-alignment-design.md:41`「R-1〜R-8 は AI 既定値で実装」）。だから「最後に見たページを覚える」で 3 タップになる場合があっても、それだけで退けず本人に聞く（§5 Q1）

### 1-4 既定ページとページ間の期間保持 → **既定は毎回「強さ」。各ページの期間は分析の中では保ち、分析を出たら全部直近**

- 期間の保持: 両派とも「保つ」で一致（10 §4-2・21 §4-5）。理由は場面 2「中身で 3 週前を見る → 強さ → 中身に戻ると 3 週前のまま」（11 §3）。保たないと、1 タップで行き来できる案A の利点（見比べ）が消える
- 期間の共有（連動）はしない: 単位が 30 日・5 週・1 週で違い、本人 Q5「連動しない」（`:28`）
- 「今どの期間か」は `PeriodNavigator` の日付範囲と、直近のときだけ出る小見出し（直近30日・今週・直近5週）で読める（`PeriodNavigator.swift:20`）
- 分析を出たら直近: 今の `weekStart = nil` と同じ考え方（`WeekAnalysisView.swift:15`）。分析を出ると状態の持ち主（コンテナ）ごと消えるので、特別な処理は要らない
- ページを切り替えるとスクロール位置は先頭に戻る（ページごとに別の List。30 §3-A）。種目詳細・部位シートから戻ったときはページ・期間・位置とも保たれる（push 中もコンテナが残る）

## 3. 実装設計

### 3-1 構造
- **コンテナ** `AnalysisView`（新規 `Views/Workout/AnalysisView.swift`）。`WorkoutView` の `AnalysisRoute` の destination をこれに差し替える
  - `@State page: AnalysisPage = .strength`（`enum AnalysisPage { strength, continuity, content }`）
  - 期間の状態をここに引き上げる: `strengthPeriod: StrengthPeriod = .recent`／`heatmapRange: HeatmapRange = .halfYear`／`monthPage = 0`／`weekStart: Date? = nil`。子へ `Binding` で渡す。部位シート `selected`・`sheet` は子に残す
  - 本体: `VStack(spacing: 0) { switch page { … } }` のように**中身が透過しないコンテナ**で包み、`.toolbar { ToolbarItem(placement: .principal) { Picker … .pickerStyle(.segmented) } }`・`.navigationTitle("分析")`・`.navigationBarTitleDisplayMode(.inline)`・先読みの `.task` をこのコンテナに付ける
  - **`Group { switch … }.task { … }` にしない**: `Group` に付けた修飾子は中の各 View に付く。`switch` の中身はページを替えるたびに入れ替わるので、`.task` がページの `.task` と同じ動き（切替のたびに取消・再実行）になり、地雷 1 (a) の意味がなくなる。各ページのブランチは必ず List を返す（空でも「記録はありません」の行。地雷 4 = memory `feedback_swiftui_task_emptyview`）
- **強さページ** `StrengthPage`（`BodyStrengthViews.swift` に追加）: `List { BodyStrengthSections(period: $period, …); ExerciseProgressSection(…) }`。`BodyStrengthSections` は `@State period` を `@Binding` に。Section 見出し「強さ」を外し、心肺の見出しに期間ラベルを出す。シート・`.task` は今どおり PeriodNavigator の 1 行に付けたまま（地雷 3）

### 3-2 ロード（地雷 1 への対策: (a)＋(b) の両方）
今のコード【事実】: `ensureLoaded` は「未ロードかつ取得中でない週」だけ取る（`WorkoutHistoryStore.swift:43`）。取得中の週を頼まれると**待たずに return**。取得は呼び出し元の `.task` の中で動くので、ページ切替・画面を出る操作でその `.task` が取り消されると、キャンセルのエラーは表示せず（`:102`）`weeks` にも入らない。後から来た側はもう return しているので、強さは「読み込み中…」のまま、ヒートマップは「記録なし」の色のまま残りうる。モックの `fetchSets` は待ちが無い（`MockWorkoutDataSource.swift:233`）ので、**今のモックでは再現しない**【事実】。Supabase では起こりうる【推測・未再現】。今の 1 枚でも「分析を出てすぐ入り直す」で同じ型になりうる。

(b) store の修正（`Services/WorkoutHistoryStore.swift`）:
- `inFlight: Set<Date>` → `inFlight: [Date: Task<Void, Never>]`
- `ensureLoaded`: 未ロードの週のうち、取得中のものはその Task を集め、取得中でないものは**store が持つ非構造化 `Task`** で 1 リクエストにまとめて取りに行く。最後に集めた Task をすべて `await` してから返す
  - 取得を store 側の Task で走らせるので、呼び出し元（View の `.task`）が取り消されても取得は続き、`weeks` に入る。後から来た呼び出しは同じ Task を待つので「待たずに return」が無くなる
  - 取得の完了時（成功・失敗とも）に、自分の Task が入っている週だけ `inFlight` から外す（invalidate 後に始まった別の取得の分を消さない）
- `invalidate()`: 今どおり世代を進め、`inFlight` を空にする。世代を `@Published private(set) var generation` として公開する
- コンテナの先読み: `.task(id: PrefetchKey(generation: historyStore.generation, week: 今週の週頭))` で 26 週を `ensureLoaded`。日跨ぎ・引っ張って更新（`WorkoutView.swift:160,293` の invalidate）で 26 週を読み直す。`loadRecordedExerciseIds` もコンテナに置く（ページ切替のたびに取り直さない）

(a) 先読みの置き場: 26 週の先読みはコンテナに置き、ページ側の `.task` は「そのページで期間を 26 週より前へ動かしたとき」の分だけ（強さ `.task(id: period)`・1 か月 `.task(id: monthPage)`・中身 `.task(id: shownWeek)`、どれも今あるもの）。(b) があればページ側が取り消されても取得は失われない。

### 3-3 ヒートマップの色のちらつき（地雷 2 への対策）
今のコード【事実】: 閾値は「今日から 26 週の窓の、**読めている日だけ**」の 4 分位（`ContinuityViews.swift:153-156`）。トレーニングタブが先に直近 5 週を読んでいる（`WorkoutView.swift:393`）ので、26 週がそろう前は 5 週ぶんの閾値で塗られ、そろうと色が変わる。継続を独立したページにすると、開いた瞬間に目の前で変わる。
